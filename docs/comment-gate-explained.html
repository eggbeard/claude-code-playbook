The Comment Gate · claude-code-playbook

A comment earns its place, or it doesn't land.

A write-time gate that blocks non-load-bearing comments in production code — judged fresh, by a party with no stake in having written them.

Kept a why the next editor needs Cut a line that restates the code

The problem

Clarity was never the deficit.

The rule is simple: a comment earns its place only when it carries a why, a constraint, a footgun, or an anchor the code cannot — never when it restates the code, a doc, or the author's own derivation. That rule lived in the project guide, in a dedicated skill, and in per-session memory, and an advisory hook flagged every offending line as it was written.

It still failed. One branch shipped roughly fifty comment lines that failed the test — with the advisory hook flagging every one — and clearing them took a dedicated sweep and an extra review round. A clearer restatement of the rule would not have changed that. The fix had to be structural.

The mechanism

Every failure mode, answered by a design choice

A stated rule decays for reasons wording can't fix, and an advisory flag lands wrong even when it fires every time. Each row pairs the failure on the left with the structural answer the gate makes on the right.

Fails · salience decay

The rule is a few hundred tokens at the top of a context that grows into the hundreds of thousands. It isn't deleted — it gets quieter.

Answered · fire at the write

The gate runs at the moment of the write (PreToolUse). There is no distance for the rule to decay over.

Fails · author-as-judge

Re-evaluating a comment you composed seconds ago, with the justification still hot, gives a precomputed verdict — self-consistency, not a fresh test.

Answered · a fresh judge

A separate context with no authorship stake, born per judgment. It has nothing to defend.

Fails · advisory on success

The write already succeeded when the flag arrived, so acting meant reopening finished work. An advisory on a success reads as FYI.

Answered · a blocking deny

The write fails. Rewriting the comment is the only way forward — compliance is the path, not a suggestion.

Fails · habituation

A flag on every added line, good ones included, builds a false-positive base rate. Each dismissal makes the next cheaper.

Answered · nothing to dismiss

Nothing is asked of the author, and the judge keeps no history — so there is no muscle to build for waving it away.

Fails · the rule goes unread

Pointing at the skill isn't reading it. The delete-test was never in context at the decision point.

Answered · the rule is the brief

The skill is the judge's rulebook, in its context at every decision — read by the party it was written for.

Fails · the exception clause

"Load-bearing only" needs a classifier, and the classifier is the same context sure that what it just wrote is the exception.

Answered · no derivation in memory

The judge applies the mis-edit test cold, with none of the reasoning that made the comment feel valuable.

Fails · cost on every write

Judging every edit would tax comment-free writes with a model call they don't need.

Answered · a cheap first gate

A regex detector escalates to the judge only when comment lines are actually added. No comment, no cost.

The flow

From keystroke to verdict

  1. A write arrives PreToolUse

    Any Write or Edit to production TypeScript (apps/**/src, libs/**/src; never specs or test utilities) enters the gate before it touches disk.

  2. The detector scans the proposed content regex · free

    It looks only for added comment lines, ignoring // inside strings. None added → the write proceeds instantly, at zero model cost.

  3. The judge rules on what was added fresh · no write/edit

    A headless model call, given the skill as its rulebook and the nearest domain docs, applies the delete-test to each added line and returns a per-line verdict. Write and Edit are disabled, so it cannot loop back through the gate.

  4. Allow, or deny with reasons verdict

    Every line load-bearing → allow. Otherwise the write is denied with the judge's per-line reasons, and the author rewrites. If the judge is unreachable after a retry, the write fails open — a failed judge is not a bad comment.

The test itself

Would the next editor mis-edit this without it?

Not "is this true and not already in the code?" — every domain fact passes that, so it filters nothing. The reader is modelled with the repo, grep, and the domain docs at hand; "need" is scoped to editing this line safely. Overlap with a doc is not grounds to cut: a doc warns "this kind of thing exists across the domain," a comment warns "this specific thing, here," and docs get trimmed too.

Operating it

The guarantees, and the seams

Zero-cost path
A write that adds no comment never reaches the judge — no latency, no model call.
No recursion
The judge runs with Write and Edit disabled, so it cannot re-enter the gate; a guard variable makes it doubly certain.
Retry, then open
A timeout or transient error retries once; still unreachable, the write is allowed and a breadcrumb is logged. A real verdict still blocks.
Review backstop
Because it can fail open, a review-time comment audit catches anything that slips through — enforcement is defense-in-depth, not one chokepoint.
Escape hatch
CLAUDE_COMMENT_GATE_OFF=1 disables the gate entirely, for emergencies.

A lesson worth keeping. The first judge, handed the domain docs and told to cut what restated them, promptly cut load-bearing footguns that merely overlapped a doc topic — quietly re-deriving a rule we had explicitly rejected. The calibration fixtures now pin both ends: measurements and consumer-lists deny; code-site footguns and whys pass. A judge is a component you test, not a rule you trust.

Reuse the pattern

Porting it to your own rule

The shape generalizes to any judgment rule that a stated instruction keeps losing — one that needs a classifier the author is the worst-placed to run.

  1. Put the rule in one place, written for the party that must apply it — not scattered across guides and memory.
  2. Detect cheaply and deterministically, so the common case pays nothing and only real candidates escalate.
  3. Judge in a fresh context that never wrote the thing under review, with the rule in hand at the decision point.
  4. Block on a real verdict; fail open on an unavailable judge — a broken tool is not a violation.
  5. Back the write-time gate with a review-time audit, and pin the judge's calibration with fixtures from real cases.
